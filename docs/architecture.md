# 架构与一次请求

## 当前调用链

~~~text
网页 / 或 /docs
    → app.py：接收HTTP请求，校验JSON
    → chat.py：按标识找角色
    → providers.py：离线适配器生成带标签的输入回显
    → chat.py：组装响应
    → app.py：返回JSON
~~~

启动时 characters.py 读取包内 data/characters 的JSON。配置不合法、标识重复或没有角色会明确失败；角色卡随安装包分发，不依赖终端当前目录。

## 四个职责

| 模块 | 当前职责 | 以后可能增加 |
|---|---|---|
| 角色配置 | 读取和验证原创角色卡 | 知识边界、配置版本 |
| 对话流程 | 查找角色、调用适配器、组织回复 | 上下文构造、检索与记忆引用 |
| 模型适配 | generate(character, message)与mode；默认mock | 一个真实模型适配器及失败处理 |
| HTTP接口 | 接收请求、返回明确的错误和JSON | 会话、流式与不同客户端 |

ChatProvider描述所需方法，不替你实现真实模型。create_app可以注入另一个适配器，测试已验证调用链不用随之更改。

## 请求与边界

POST /api/chat接收character_id、message；返回character_id、reply、mode。只有单轮输入，没有会话ID、数据库或历史上下文。

网页展示persona，并把greeting作为进入角色对话时的开场白。模拟器仍只使用名字和输入，未执行人物设定。以后研究Prompt时再决定怎样使用这些字段。

## 网页客户端

`web/index.html`、`styles.css`、`app.js`由同一FastAPI服务提供，静态资源挂载在 `/assets`。不需要Node.js、前端构建或第三方CDN，资源随Python包分发。

页面请求角色列表和服务模式；发送时只提交角色标识与当前文本。每个角色的消息暂存在浏览器内存中，刷新后清空，不属于后端会话或模型记忆。清空按钮只影响当前角色的本页记录。输入和角色资料使用textContent显示，避免把消息当HTML执行。

发送期间锁定角色切换和清空，避免把异步回复放入另一位角色的对话。失败时保留输入供重试，30秒后显示超时提示；网页同时处理空白、超长输入和角色加载失败。

示例配置属于可公开资料。正式系统若有隐藏设定，要重新设计对客户端公开的信息；当前接口不提供这些保证。

## 后续能力怎样接入

- 知识：检索模块输出有来源的片段，再由对话流程决定怎样提供给模型。
- 记忆：先区分聊天记录、近期上下文与长期记忆，研究更新、隔离、查看和删除。
- 评测：作为独立实验固定问题、评分与配置，不靠界面截图判定效果。
- 客户端：网页或游戏客户端调用同一HTTP服务，接入前先理解请求与响应。

这些是扩展方向，没有隐藏实现。新增接口、数据格式或行为时更新文档和测试。
